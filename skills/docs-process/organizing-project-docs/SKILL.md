# 项目文档四分法（来源分离）

**一句话规则：别人给的原文只读存档；我们的理解、状态、踩坑各自独立成文；README 索引标明每份文档的 名称/来源/用途/维护约定。**

混在一起的代价（真实教训）：需求理解散落在对话里变成"第524行清单"式黑话；改了客户原文就再也没法对照源头；踩坑混进接口文档，下个人分不清哪句是官方说法哪句是实测纠正。

## 四类文档，各自独立成文

| 类 | 是什么 | 铁律 |
|---|---|---|
| ① 原文快照 | 客户/第三方给的需求、规格、验收单（含原始格式存档） | **只读，永不编辑**——发现错误写进②的差异表，不改原文，保证永远可与源头对照。异构原件（docx/pdf）**再转录一份可搜索的 `客户需求.md`**（见下），日常查客户诉求走它 |
| ② 内部理解文档 | 我们消化后的需求理解：每模块的本质、裁决原则、**与原文的差异决策表** | 差异表三列：差异内容 / 原因 / 确认状态（**已确认 · 默认执行 · 待确认**） |
| ③ 外部 API 参考 | 对接的每个外部接口一篇：**request URL + 实测 request/response 样本** + 字段、与我方字段的映射 | 来源=官方文档＋实测；每篇必带真实 request/response 样本（光散文描述字段不算数）；按接口分文件，便于查证 |
| ④ Gotchas 踩坑笔记 | **官方文档没写或写错、实测才知道的点**，与③分开放 | 每条四段：现象 / 官方怎么说 / 实测是什么（带证据如 request_id）/ 我们代码怎么处理。**实测 > 官方文档** |

外加两份状态文档（与②分工明确，别混写）：
- **完成度对照表**：对照①逐条 ✅已完成/🔶部分(缺什么)/❌未做/➖不做(原因)，每上线一项就更新，完成状态以它为准；
- **开发过程 todo**：工程视角滚动记录，允许乱，对外状态不看它。

## ③ 每个接口至少要落这些（可复核 > 散文）

学一个外部接口（尤其是结构复杂的第三方开放平台接口），文档里**至少**要有：
- **request URL**：完整路径 + 方法，如 `POST /v1/report/xxx`。
- **request 样本**：真实发过的关键参数/body（连同限制，如「单次跨度 ≤7 天」「某枚举参数需为特定值」）。
- **response 样本**：真实返回，能看出**字段真名 / 层级 / `code`·`message`**；截断可以，别改写。
  异步接口把**产物**一并记（如 CSV 表头、列数、BOM、轮询状态码）。
- 字段说明 + 与我方字段映射。

理由：光用散文描述字段，下一个人（含未来的我）无法复核**字段真名、是否真返回、口径**——
**样本才是证据**（呼应 [[no-fudging]]「只用验证过的事实」）。实测样本里的字段名/层级/code，
比记忆和官方文档都靠谱（用只读探针实测抓到的样本尤其可靠）。

## README 索引（docs/README.md）

按来源分区列表：**客户给的（只读）/ 我们写的（工作产物）/ 外部抓取+实测**，
每行=文档名 · 来源 · 用途 · 维护约定。新文档必须入索引。

## 客户又发来一版：追加/反馈文档的接收仪式

①原文**不止最初那份**——客户会陆续追加需求/验收反馈（如「问题1.1」「问题1.2」）。
**每收到一版就跑这套仪式，动手做它里面任何一条之前先跑完**：

1. **存档 + 入索引**：存为①原文快照、加进 README 索引（哪版 / 日期 / 来源）。
2. **逐条对账**：把它每个问题/期望**逐条**抽进 ②差异决策表 + 完成度对照表，每条给状态
   （已确认 / 默认执行 / 待确认；✅/🔶/❌/➖）。完成度必须覆盖**所有**①原文（原始规格 +
   每一版反馈），不是只盯最初那份。
3. 抽条**照原文逐字**（含它的示例 / 校验 / 例外），别凭对话里的二手转述——转述会丢示例、改口径。

漏了这套的真实代价：一份客户反馈（含一段完整的组合/优先级示例）被丢进 docs/ 却没入索引、
没进完成度，需求在里面烂了整整一段时间，直到客户拿原话重述才被发现；期间还照二手理解
做错了一版、返工重做。

## 客户需求转录 md（①的可搜索面，别每次去解 docx/pdf）

原件 docx/pdf/异构文件存档只读、但**搜不了、读着累**（要解压 XML、翻截图、跨好几份文件）。
所以①除了原件存档，再维护一份 **`客户需求.md`**——把客户原文**逐字/近逐字**搬进 md，作为
日常查客户诉求的**唯一入口**（客户文档多、还不断出新版，尤其需要这层）：

- **尽量少掺自己的话**：这里放**客户的原话**（我们的理解、判断放②，别混进来）。照抄——连它的
  示例、校验、边界、甚至错别字都原样留，方便日后逐字对照。
- **每条标来源**：哪份文档 / 日期 / 版本（原始规格 / 问题1.1 / 问题1.2 …）。
- **记更新轨迹**：客户改了某条，在原条下**追加**一行「→ <日期><哪版> 改成…」，别覆盖旧的——
  一眼看出这条需求跨版本怎么演变。
- **可挂轻量指针到②/完成度**：条目旁一句「我们的理解见②X ／ 这条疑似错→②差异表 ／ 已拆成
  子项 a·b·c ／ 状态见完成度」，但**不在这里展开我们的判断**（判断在②，保持这份"接近纯客户话"）。
- 按模块组织，跟②、跟完成度对得上。

好处：以后查"客户到底要啥"只 grep 这一份 md，不用解 docx、翻 pdf；漏跟踪也更难发生——新一版
反馈进来，"转录进 `客户需求.md`" 就是上面「接收仪式」第 1 步的自然落点。

## 裁决顺序（三源原则，泛化）

需求方文档决定「要不要做」；官方 API 文档+实测决定「能不能、字段叫什么」（冲突以实测为准）；
产品界面实况决定「长什么样、默认值」。不确定的默认值按需求方意图先做（可见可纠错的错误宁可犯），
并在②的差异表记「默认执行」。

**判「客户填错/不做」的硬门槛**：需求方文档说要做的，你要判它「填错 / 疑似错误 / 砍掉 / 不做」
之前，**必须回①原文逐字读那一条**（含示例、校验、边界），拿①原文当依据——不能凭拍平的 Excel
行序、截图、或对话里的二手理解就给客户判错。呼应 [[read-the-encoding]]（结构事实只在编码源，
渲染物/转写会丢结构）、[[no-fudging]]（只用验证过的事实）。真实教训：把客户需求里一段完整的
组合/优先级示例，误读成一句简化规则、当笔误砍掉，其实是从没有回原文逐字核对那几行示例。

## 危险信号自查

- 正要**编辑**一份别人给的原文 → 停，写进②差异表
- 需求理解/决策只出现在对话或记忆里 → 落盘到②
- 把"文档没写、实测发现"的结论写进③接口文档正文 → 挪到④，标明是实测
- 汇报里用行号/内部编号指代需求（"第524行那节"）→ 用章节名，状态指向完成度表
- 客户发来新一版反馈/追加需求文档，我准备直接开做某条 → 停，先跑「接收仪式」（存档 + 入索引 + 逐条进完成度）
- docs/ 里有客户原文没进 README 索引 / 完成度表里找不到某份①原文的条目 → 那份需求正在烂掉
- 我准备判客户某条「填错/不做」，却没回①原文逐字核对那一条 → 停，回去读原文再判
