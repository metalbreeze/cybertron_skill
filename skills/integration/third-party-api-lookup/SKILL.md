# 查阅第三方平台 API（开放平台文档查阅法）

把"某个第三方开放平台接口到底长什么样"从猜测变成可查证：通过开放平台文档站搜索 → 进文档 → 抓字段 → 落库。

## 何时用

需要某个第三方接口的**真实定义**（路径 / 请求参数 / 返回字段 / 文档编号）时。典型场景：给项目新接一个"列举可选项"的代理接口（分类树、模板、落地页、文案库……），或核对某字段的合法取值。**不要凭空编接口路径/字段**——接错了下游会失败。

## 前提

- 有能访问该开放平台文档站的浏览器环境（多数平台文档站需要登录态；查文档是只读操作，安全）。
- 用**新标签页**查文档，**别动**任何"live"的编辑/投放页面——很多平台的网页控制台和文档站不是同一套系统，误点保存/退出会改到线上数据。

## 步骤

1. **搜索**：导航到平台文档站的搜索页（形如 `https://<docs-host>/search?keyword=<URL编码关键词>`）。
2. **看结果**：结果常按子产品线分 tab，先选对产品线；每条结果一般显示接口标题 + 路径片段 + 示例，先扫一眼定位目标（注意区分 create/update/**details(查询)**/list）。
3. **进文档**：很多文档站把"文档编号"放在 URL 的 query 里（如 `?docType=xxx&documentId=NNNN`）——记下来，回填给用户、记进项目文档。
   ⚠️ 有些文档站**点击搜索结果不触发路由跳转**（点了 URL 不变），别死磕点击。更可靠的办法：从搜索结果项的 DOM 属性（如某个 `data-key` 属性）里直接取文档编号，再手动拼 URL 跳转。文档编号往往**不连续、不能顺序猜**，每个都要单独查。
4. **抓字段（层级在 DOM 里，不在文本里）**：
   ⚠️ **别用"取整页纯文本"的方式判断层级**（例如页面转文字的工具）。它会把「请求参数表」的**行缩进抹平**，而缩进正是唯一的层级信息。
   ⚠️ **也别指望"请求样例"**——复杂接口常常**根本没有**这一节；参数表里的"示例"列也可能大多是占位符，不是嵌套 JSON。
   ⚠️ **也别人工/视觉转写**（照着渲染页手动重建 JSON）——比纯文本强，但**照样会拍平**嵌套结构。

   ✅ **正确做法**：很多文档站的参数表是**树形表格组件**（如 Ant Design 的 Table），层级**直接写在每一行的 class 上**，例如 `tr.ant-table-row` 的 `ant-table-row-level-N`（N=0 为顶层）。取纯文本的工具只取文字，会把这个信息整个丢掉；改成读 DOM 的 class/属性，一次性拿到每一行的真实层级，再按**行序**把层级和文本表里的字段名/类型/描述 join 回去。

   导出 `(level, 字段名, 类型, 必填, 描述)` → 按 level 重建嵌套 → 存成一份带层级的 JSON/JSONC（类型/必填/枚举/约束写成**行内注释**）。
5. **落库**：为每个接口写一篇简短文档，记录路径、文档编号、关键约束、与自己项目字段的映射，并**链到那份结构化 JSON**。**复杂接口（字段多、嵌套深）必须有对应的 JSON**，不能只留一张拍平的表。返回字段表里常顺带引用其它接口路径（一次查到多个），留意收集。

## 🔴 拍平的字段表表达不了层级——禁止从行序推嵌套

**很多平台文档的「请求参数表」（以及它的 Excel 导出 / 取纯文本的结果）是一棵被拍平的树：
对象字段的子字段直接内联在它下面，而「子字段到此结束」没有任何标记。**
于是「对象的最后一个子字段」和「下一个顶层字段」在表里**长得完全一样**。

踩过的真实事故：某接口里有一个**顶层**字段，本应与另一个对象字段**平级互斥**，但在参数表里它紧跟在那个对象的最后一个子字段后面 → 被人读成了那个对象的子字段 → 提交时嵌套错了位置 → 第三方平台**返回成功、静默丢弃了这个字段** → 对应功能实际没生效，直到线上复核才发现，被判定为严重事故。

**这不是"读仔细点"能救的。** 用改名同构的表复测：多个独立的人/agent **全部**把顶层字段判成了子字段；其中还有反过来要求把**本来正确的顶层字段**"搬进"对象里的（照做会制造新 bug）。

**规则：**
- ❌ **不得**用行序推层级。尤其别用这条自造规则：「子字段一直排到下一个『必填』字段为止」——实测就是它把人带沟里。
- ❌ **自己项目里的文档、代码、commit 历史不是层级证据**——它们可能正编码着你要查的那个 bug（连"派 subagent 复核"也会被污染：如果仓库里已经写着错误答案，subagent 会**背**而不是**推**）。
  ⚠️ **转述即篡改**：引用官方原文要**逐字照抄**，别顺手加限定词——多加一个字就可能把"关联后作废整个兄弟对象"悄悄改写成"关联后作废对象内部的其它字段"，一个词就把 bug 合理化了。
- ✅ **取保留层级的原文**：见步骤 4（读 DOM 行缩进 → 重建嵌套 JSON → 落库）。
- ✅ **结构神谕：回读同名实体（最省事，通常只读、不用登录、不用真正创建东西）**——
  很多平台的 `list`/`details` 类接口返回的实体，其 JSON **本身就带着真实层级**。能拿到这类"回读"接口时，直接读它比抠文档参数表可靠——一眼能看出两个字段到底是不是并排的顶层键。
  ⚠️ 边界：这是**强证据、非铁律**——只读接口可能省略仅创建时可用的字段、或多出只读字段；能对上的字段按它定，对不上的仍以文档嵌套原文为准。
- ⚠️ 实在拿不到嵌套原文时，下面两条只能用来**质疑**、不能用来**定论**：
  - **类型列是自定义对象名**（不是 String/Integer/Boolean 这类基础类型）→ 大概率是对象，子字段内联在下面；
  - **描述里的关系句是决定性的**：「关联后 **X 字段失效**」⇒ 与 X **平级**（能作废 X 的必是它兄弟）；
    「需嵌在 yyy 对象里」⇒ 是子字段。

## 🔴 类型逐字抄，别按字段名猜

同一接口里相邻的两个"开关"类字段，类型可以不同——名字长得像的两个字段，一个可能是 **Integer**（0/1），另一个是 **Boolean**（true/false）。发错类型的后果通常是**静默忽略**，功能没真正打开。

**字段名里带 `_switch` / `_explore` / `_enable` 这类词，推不出真实类型就是 Boolean。** 类型永远照抄接口文档的类型列，不要靠字段名猜、也不要因为"隔壁那个同类字段是 Boolean"就类推。

## 🔴 `code:0`（或任意成功状态码）≠ 字段生效（必须回读实体）

很多平台对**层级放错**或**类型发错**的字段是**静默丢弃**，照样返回成功状态 + 新建的 id。所以"接口收下了""返回了新建 id"**不能证明任何一个字段生效**——更不能拿来"验证"层级。

**自建自验回路（推荐做法）：**

1. **建**（选无副作用/零成本的方式：置为暂停态、用显眼的测试前缀命名，避免影响真实数据）。
2. **回读**：用对应的查询/`list`/`details` 接口把刚创建的实体**读回来**。
3. **断言**：你发的字段在**回读到的实体上存在、且值相同**，才算生效。
4. 如果平台调用链路有出入站日志，核对实际发送的请求体原文。
5. **收尾**：清理掉测试数据。

## 红旗——冒出这些念头就停下

- "第 N 行排在某字段后面，所以它是那个字段的子字段"
- "子字段一直排到下一个『必填』字段为止"
- "我们自己的文档/代码就是这么写的，应该没错"
- "接口返回成功且给了 id，说明位置对/字段生效了"
- "这个字段类型看名字应该跟另一个一样"

**以上任何一条出现 = 你正在复现同一类事故。去拿嵌套原文，然后回读实体。**

| 借口 | 现实 |
|---|---|
| "表里某字段紧跟一个对象的子字段，那就是子字段" | 拍平表**不含**层级信息；最后一个子字段与下一个顶层字段无法区分。改名复现里参与者**全军覆没**。 |
| "返回成功且有 id，位置没问题" | 实测过：嵌套错误的请求同样返回成功 + id，而对应功能是空的。 |
| "我方文档写的就是这个嵌套方式" | 我方文档可能正是 bug 本身。**只有官方原文 + 回读到的实体**算证据。 |
| "字段名一看就是开关，应该是 Boolean" | 名字像开关的字段，类型可能不同。照抄类型列。 |
| "字段太多，嵌套 JSON 太费事，表够用了" | 那张表正是事故的来源。复杂接口不产出结构化 JSON = 把下一个人推进同一个坑。 |

## ⚠️ 空白文档页 ≠ 接口不存在

部分文档页正文是**内嵌的第三方文档系统**（如某种在线文档 iframe），SPA 首屏常渲染空白/转圈，取整页文本只能看到标题和更新时间。**别据此断定"接口不存在"**——正确读法是找到内嵌 iframe 的真实地址，直接跳转过去，才能取到全文。判别信号：页面只有标题+更新时间、DOM 里有 iframe。跳转后往往要**多等几秒**（首屏转圈），第一次取文本可能失败，稍等重试即可。

## ⚠️ 文档 vs 实测不一致（以实测为准，二分探边界）

文档也会错/过时，接入后**必须用只读方式实测**。常见的两类偏差：
- 日期/数值**格式**文档写的和接口实际接受的不一致；
- **时间窗口/取值范围**文档没写清楚，需要实测二分边界（改一维、二分逼近、记下返回的错误码/消息）。

结论连同复现方式（请求参数 + 返回的 code/message）固化进项目的 API 参考文档，可供平台侧核对。

## 逐字读权威源（判别技巧——别漏括号里的限定词）

> 真相只有两个权威源：**平台的实际操作界面**和**官方开放平台 API 文档**。**逐字读它们，每一个字都读，尤其是括号/小字里的限定词**——这些限定词往往是决定性的，漏一个就会做出错误判断、上线后被平台拒绝。

**界面上的决定性限定词（小括号 / 灰字 / 角标）**，一定要读进去再下判断：
- **`(即将下线)` / `(已下线)` / `(灰度中)`** → 这个选项**不能选/不能用**了。
- **`(白名单)` / `(需加白)`** → 普通账户用不了，得账户先申请加白，否则接口报错。
- **`(不可改)` / `(添加后不可修改)`** → 创建时定死，别做成可编辑控件。
- **`(默认xx)` / `(不填默认yy)`** → 不传时的真实行为；决定要不要显式发、发什么。
- **`必填` 的条件句**（"当类型为…时必填"）→ 必填是**有条件的**，条件成立才必填——既不能漏发，也不能无条件硬发。

**API 文档同理**：字段「描述/备注」里每一句都读完——`xxx 时必填`、`xx 不支持`、`需嵌在 yyy 对象里`、`仅 zz=1 时生效`、`白名单功能`。漏读一句限定词，就可能把本该嵌套的字段发到顶层、或漏掉一个条件必填。

**三源交叉**：字段**要不要做** = 业务需求方文档；**存在/名称/条件** = 官方 create API 文档；**界面形态/顺序/可选与否** = 实际操作界面（含上面这些限定词）。任何一处的小字都可能推翻你的结论——**读完每一个字再下判断，别脑补**。

## 要点 / 陷阱

- 开放平台接口和"网页内部接口"通常是两套不同的鉴权/路径体系——从网页控制台的 network 面板抓到的接口，很可能后端根本用不了。接入时认准官方"开放平台"文档，不要凭网页抓包猜。
- **列表类接口**常见「ID 与分页二选一」：不传 id 列表、改传 `page`/`page_size`，即可**列出全部**——下拉数据源常常就靠这个。
- 文档页一般有版本号和更新时间，确认自己看的是不是最新版本。
- 路径偶有笔误（如出现双斜杠）——接入时按实际请求做归一化。

## 接入项目的统一三段式

1. 后端加一个 `FetchXxx(ctx, ...)` 方法，调用第三方接口；
2. 后端加一个内部代理路由（鉴权 + 参数转发），供前端调用；
3. 前端把写死的 mock 选项换成对这个代理路由的查询，用返回的 `{value,label}` 渲染下拉/级联选择器。

## 已验证接口速查（在自己项目里持续维护）

给每个接过的接口留一行记录，团队核对字段时先查这张表，比翻聊天记录、翻 commit 靠谱：

| 用途 | 路径 | 文档编号 | 结构备注（DOM 实测） |
|---|---|---|---|
| 示例：创建某资源 | `/v1/resource/create` | `<doc-id>` | 顶层 N 键 / M 层；`config` 对象含若干子字段，顶层另有一个与之互斥的字段 |
| 示例：查询该资源（回读验证用） | `/v1/resource/list` | `<doc-id>` | — |
