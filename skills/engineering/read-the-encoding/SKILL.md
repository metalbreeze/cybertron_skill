# 读编码源，别读渲染物

## 核心

结构性事实（**层级、成员边界、类型、必填**）只存在于**编码源**里。
**渲染物**是编码源的有损投影：它把结构烧成视觉，而导出/截屏/取文本又把视觉抹掉。

**拍平的表里，「对象的最后一个子字段」和「下一个顶层字段」长得一模一样。**
没有任何标记划出边界——**这不是「读仔细点」能救的**。

## 渲染物 → 去哪儿找它的编码源

| 渲染物（**不可**作为结构依据） | 编码源（**唯一**依据） |
|---|---|
| 文档站导出的字段表 / Excel / 复制粘贴的表 | 页面 DOM 的层级属性：class `depth-N` / `row-level-N`、`aria-level`、缩进容器 |
| 截图 / `get_page_text` / 渲染后的 HTML 文本 | 页面背后的 JSON、OpenAPI/schema 端点 |
| CLI 的 `--help` | argparse / cobra / clap 里的参数定义源码 |
| 打印出来的表格、日志里的对齐输出 | 原始 CSV / JSON / 结构化日志字段 |
| 别人（或你自己）**手工/视觉转写**的 JSON | 上面任意一个（转写照样会拍平） |
| 「上游返回 200 / code:0 / 新建成功」 | 把实体 `GET` / `list` **回读**，看字段在不在、值对不对 |
| **声明编码的元数据**：ZIP 的 UTF-8 标志位、HTTP `Content-Type; charset=`、XML 声明、`<meta charset>` | **字节本身**：拿候选编码去解，看结果是否合法（`utf8.ValidString` / `codecs.decode(..., errors='strict')`） |

## 该怎么做

1. **问一句：这份东西是从什么生成的？** 去读那个东西。渲染物总有来源。
2. **找编码位**：class / 属性 / 缩进容器 / schema / AST / 源码定义。**先探再抓，别猜选择器。**
3. **回读验证**：上游「收下了」从不等于「字段生效了」——错层级、错类型的字段常被**静默丢弃**。
4. 拿不到编码源时 → **不要产出具体结构**（见下）。

## 结构不可判定时，输出长这样（recipe）

**不是**「最可能的 JSON + 免责声明」。**免责声明不会跟着 JSON 被复制走**——
下游只会拷贝那段结构，脚注留在原地。

输出三段：

1. **已确证**：逐条写清依据（「表里写死」/「描述明说『关联后 X 失效』⇒ 能作废 X 的必是 X 的兄弟」）。
2. **不可判定**：把字段**列出来，不给位置、不给值**。别塞进任何对象，也别放顶层。
3. **下一步**：取编码源的**具体**动作——读哪个 DOM 属性、请求哪个 schema 端点、调哪个 list 接口。

## 特例：声明编码的标志位是**单向**可信的

编码声明（ZIP 的 general purpose bit 11、`Content-Type: charset=`、`<meta charset>`）
是**关于**字节的一句断言，不是字节本身。它和渲染物是同一类东西：**二手的**。

而且它的可信度是**单向**的：

```
标志位 = 1  ⇒  确实是 UTF-8        （置位是主动行为，可信）
标志位 = 0  ⇏  确实不是 UTF-8      （不置位可能只是懒得置，不可信）
```

真实代价：一个"从 zip 包导入中文文件名"的功能。ZIP 规范说 bit 11 置位表示文件名是 UTF-8，
于是很自然写成「没置位 → 按 GBK 解」。**两个主流打包器都不置位，但字节编码完全相反**：

| 打包方 | bit 11 | 实际字节 | 「没置位→GBK」的结果 |
|---|---|---|---|
| Windows 资源管理器 | 0 | **GBK** | ✅ 对 |
| macOS Finder / `ditto` | 0 | **UTF-8** | ❌ 拿 UTF-8 当 GBK 解 → 整片乱码 |

只在 Windows 包上测过，会一路绿灯到用户手里。修法是**别问标志位，去问字节**：

```go
// 标志位只能证明「是 UTF-8」，不能证明「不是」——所以先验字节，验不过才回退。
if ze.NonUTF8 && !utf8.ValidString(name) {
    name, _ = simplifiedchinese.GBK.NewDecoder().String(name)
}
```

**顺带一个造测试数据的坑**：Python 的 `zipfile` 遇到非 ASCII 名字会**自动**置上 bit 11。
所以"用 Python 写个 GBK 包来测"默认造不出真实的 Windows 包 —— 得 monkey-patch
`ZipInfo._encodeFilenameFlags` 把标志位按住。**测试夹具本身也要验编码源**，
否则你验证的是自己的想象。真实排查里就先造了一个假的"GBK 包"、白测一轮。

## 危险信号——冒出这些念头就停

- 「它紧跟在那个对象后面，应该是它的成员」
- 「子字段一直排到下一个『必填』字段为止」
- 「先按最可能的结构写，注释里标一下不确定」
- 「文档就是这么导出的，应该没错」
- 「上游返回成功了，说明字段生效了」
- 「标志位说不是 UTF-8，那就按本地编码解」——**未置位不代表不是**，先 validate 字节
- 「测试夹具是我自己造的，肯定对」——造夹具的库也会替你改元数据
- 「去问对方/等对方确认吧」—— **而编码源就在手边**（DOM / schema / list 接口）

| 借口 | 现实 |
|---|---|
| 「我标了『推断』，不算敷衍」 | 你交付的 JSON 会被原样拷进代码，标注不会。标注≠不产出。 |
| 「字段名/语义看得出归属」 | 语义猜层级正是事故来源：某接口的 `template_id` 名字像定向、实为顶层，不在 `target` 里。 |
| 「去读 DOM/schema 太绕」 | 一次探针 vs 一次线上事故。 |
| 「返回成功了」 | 静默丢弃就是「成功」的样子。回读实体才算。 |

## 实战代价

`template_id` 是接口的**顶层**字段，却在导出的扁平表里紧跟着某个对象的最后一个子字段。
于是被当成子字段发了出去 → 上游返回 `code:0` → 字段**静默丢弃** → 定向整体失效，
客户判定「严重事故」。层级其实一直明写在文档页 `tr.ant-table-row` 的
`ant-table-row-level-N` 上，只是被 `get_page_text` 抹掉了。

同一批手工转写稿里，用编码源一扫，另外**两处同类错误**当场现形（9 个子字段被提到顶层、
一个顶层字段被嵌进数组元素里）。
