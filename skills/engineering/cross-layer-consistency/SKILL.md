# 跨层落实一致性检查（Cross-Layer Consistency）

**一句话规则：任何"看起来会影响最终提交结果"的字段/选项/联动，必须在四层全部落实；某层没落实 = bug。**

```
【1 UI 显隐/可选】 → 【2 前端 payload + 前端校验】 → 【3 后端下发(生成器/构造器)】 → 【4 第三方接口校验】
```

这是多层架构项目（前端表单 → 后端 → 第三方 API）里很常见的一类坑。本质：**某一层对规则的理解，没在另一层落实**，于是"界面看着对、实际没生效"，或"选了被静默丢"，或"传了下游不收"。

## 何时**必须**跑这个检查（强制）

- 新增 / 修改任何前端表单字段、开关、下拉选项。
- 新增 / 修改任何**变量联动**：A 取某值 → 强制 / 禁用 / 限定取值集 / 条件必填 B。
- 排查"生成出来和界面/源对象不一致""选了没生效""创建被下游拒绝"。
- 审计幽灵控件 / 只显示不下发 / 继承值丢失 / 静默丢弃。

## 三种失败形态（都要照）

| 形态 | 症状 | 缺的是哪层 |
|---|---|---|
| **A 幽灵控件** | UI 有控件，用户以为生效，但后端结构体没字段 / 生成器没读取下发 | 缺【3】链路根本不存在 |
| **B 显示≠下发**（含"继承/复制值不下发"）| UI 用 `override \|\| source` 显示继承值，看着有；但 payload 只带显式覆盖、不兜底源值 | 缺【2】payload 没做和显示一样的兜底 |
| **C UI 给了后端丢** | UI 提供了某选项，但后端/第三方接口会静默过滤/拒绝它，UI 不收窄也不提示 | 缺【1】UI 没按【3】/【4】的限定收窄 |

> 关键认知：**描述"规则存在"≠"规则四层都落实"**。后端有个正确的过滤器（【3】对）不代表 UI（【1】）按它收窄了——C 型就是这么漏的。审每条联动都要逐层问"这层落实了吗"，**列出没落实的层**。

## 四层检查清单（逐字段/逐联动过）

**【1 UI 显隐/可选】**
- 该字段/选项在不该出现的上下文里，是否 disabled / 隐藏？（如某类型下应禁用某配置区域、某开关关闭时应隐藏对应入口）
- 联动源变了，UI 是否把不再合法的选项收窄掉？（如某总开关打开后，可选范围应收窄到下游允许的子集，别让用户选了被【3】静默丢）

**【2 前端 payload + 前端校验】**
- 真正发给生成/提交接口的对象里，**这个值真的在吗**？
- 凡 UI 用 `override || source.details.X` **显示**的字段，去 payload 构造处确认**有同样的 `|| source` 兜底**——没有就是 B 型"只显示不下发"。
- 必填/阈值/互斥，前端有没有挡（block / warning）？

**【3 后端下发】**
- 后端请求结构体有没有对应字段（json tag 一致）？
- 生成器/构造器**真的读取该字段并写进发往下游的请求体**了吗？
- 联动（强制/限定/默认）在后端是否落实？过滤掉的值有没有兜底默认？

**【4 第三方接口校验】**
- 下游平台是否真有这个字段/取值？是否条件必填 / 白名单 / 即将下线 / 不可改？（用 skill `third-party-api-lookup` **逐字读** doc + 界面限定词）
- 有没有"声明 vs 实际"差异？可用只读探针实测（见下）。

## 已故障记录清单（照着别再犯，示例已抽象为通用模式）

- **A 幽灵控件**：新增了一个"出价/数值覆盖"类字段，前端展示、也让用户填，但后端结构体和生成器根本没有对应字段——填了也不会生效。
- **A 幽灵控件（变体）**：新增了几个开关型字段，UI 上能勾选，但后端接口结构体一直没补上对应字段——勾了也没有真实链路。
- **B 显示≠下发**：某个"继承自模板/源对象"的字段，UI 用 `override ?? source` 兜底显示，让用户以为继承生效；但 payload 构造只带显式覆盖值，没做同样的 `?? source` 兜底——生成结果丢了继承值，且往往是影响面很大的核心配置（如整体定向/匹配规则），一旦漏了兜底后果严重。
- **C UI 给了后端丢**：后端对某个枚举字段有一个"允许值子集"的静默过滤器，但 UI 仍展示全集选项；用户选了不在子集里的值，创建请求被后端过滤/下游拒绝，UI 既没收窄也没提示。
- **C 变体·表单误复用**：把一个为场景 A 设计的完整表单（维度很全）直接复用给约束更窄的场景 B，没有按场景收窄可见选项集，结果场景 B 里出现了一批实际不被下游接受的选项。教训：**复用表单也要按目标上下文重新核对【1】层的可见集**，别想当然认为"能用在 A 就能原样用在 B"；用两组真实上下文（A vs B）对比检查，差异一眼可见。

## 怎么快速定位各层（在你自己的代码库里）

- 【1】【2】前端：表单/面板组件（字段的显隐、可选项来源）、payload 构造与合并逻辑（提交前"真实发送对象"在哪里拼出来的，通常是一个专门的 builder/合并函数）。
- 【3】后端：接收请求的结构体定义（有没有对应 json 字段）、把请求转成下游调用的生成器/构造器代码（是否真的读取该字段并写进下游请求体）。
- 【4】第三方接口：官方文档 + 实测；不确定就用 skill `third-party-api-lookup` 查，或用下面的只读探针实测。

### 只读探针（实测【4】，禁止任何 create/变更接口）

对平台自身后端（或第三方平台）暴露的**只读查询类接口**（如账户列表、元数据字典、枚举值查询）做差分探测：固定其它参数、每次只改一个维度，对比返回结果的变化，从而反推某个字段/联动在下游到底是怎么生效的。

**硬约束：只调查询/lookup 类接口，绝不调用任何 create/update/delete 类接口，也不要在界面上点提交/保存。**

## 产出

每跑一次，对受影响的字段/联动输出一张**四层落实表**：

| 字段/联动 | 【1】UI | 【2】payload/校验 | 【3】后端下发 | 【4】第三方接口 | 缺口 |
|---|---|---|---|---|---|
| 例：总开关 A → 可选范围 B | ❌ 未按下游限定收窄 | — | ✅ 已过滤到允许子集 | ✅ 下游报错确认 | C 型：UI 该收窄 |

**任一层 ❌ 就是要修的 bug**。修法：把缺的那层补成和其它层一致（A→接后端字段或删控件；B→payload 加 `|| source` 兜底；C→UI 按后端/下游限定收窄）。能加纯函数单测就钉死。
